# Prisma ORM 8 and Effect 3.22 research

**Retrieved:** 2026-09-21  
**Scope:** upstream behavior relevant to this package's Prisma input boundary, generated Effect Schema/Kysely types, runtime helpers, package metadata, and supported runtimes. This is deliberately not a general Prisma or Effect feature list.

> **Status:** Historical pre-cutover snapshot. Its Prisma 8 findings retain their
> retrieval-date meaning, but its Effect 3 repository-state statements are
> superseded: this repository now targets exact `effect@4.0.0-rc.117` and is
> generator-only. Use `README.md`, `CLAUDE.md`, and `effect-4-api-audit.md` for
> the current Effect contract.

## Executive result

There is **no stable Prisma ORM 8 release** to adopt as of the retrieval date. Prisma documents ORM 8 as a release candidate; npm's `latest` tag resolves to the prerelease CLI `prisma@8.0.0-rc.15`, and PostgreSQL support resolves separately to `@prisma/orm-postgres@8.0.0-rc.11`. Prisma expects GA in October 2026. The repository should remain a Prisma 7/DMMF generator for now and must not claim Prisma 8 support merely because the CLI's `latest` tag is on 8. [Prisma release status](https://www.prisma.io/docs/orm/release-status) · [CLI registry record](https://registry.npmjs.org/prisma/latest) · [PostgreSQL runtime registry record](https://registry.npmjs.org/@prisma%2form-postgres/latest)

Effect is different: the npm `latest` tag is the stable **`effect@3.22.2`** (released 2026-09-09), while Effect 4 remains an RC (`4.0.0-rc.117`). The package's peer range already admits it; the Bun lock resolves the development dependency to `3.21.2`. No Effect API change found between those versions requires a source change here. [Effect npm registry](https://registry.npmjs.org/effect) · [3.22.2 release](https://github.com/Effect-TS/effect/releases/tag/effect%403.22.2)

## Prisma ORM 8: material changes and package impact

### 1. The generator protocol disappears

Prisma 8 removes `generator` blocks and `datasource` blocks from the contract. `prisma contract emit` produces `contract.json` and `contract.d.ts`; it does **not** invoke the Prisma 7 custom-generator protocol. This package's executable imports `generatorHandler` from `@prisma/generator-helper`, and its orchestrator accepts `GeneratorOptions.dmmf`; its Prisma, Effect, and Kysely generators all consume `DMMF.Document`. Therefore a Prisma 8 project cannot run this generator through a contract file today. [Prisma 7-to-8 reference](https://www.prisma.io/docs/orm/coming-from-prisma-orm-7#schema) · [`contract emit`](https://www.prisma.io/docs/cli/contract-emit) · [generator-helper's upstream stability warning](https://github.com/prisma/prisma/blob/7.8.0/packages/generator-helper/README.md)

**Consequence:** this is the blocking compatibility boundary. The existing `contract.d.ts` test fixture does not change that conclusion: there is no production reader for `contract.json` or `contract.d.ts` in `src/`.

### 2. Prisma 8's model shape is not a transparent DMMF rename

The v8 contract changes source constructs that this package currently infers from DMMF:

- field-native database types become field types (`String @db.Uuid` becomes `Uuid`); `Json` from v7 maps to `Jsonb` for the same PostgreSQL storage; and `@updatedAt` becomes `temporal.updatedAt()`; [Prisma comparison](https://www.prisma.io/docs/orm/coming-from-prisma-orm-7#schema)
- Prisma 8 has named database types, value objects, variants, and extension types in its contract model; [PSL contract authoring](https://www.prisma.io/docs/orm/contract-authoring/psl-syntax)
- implicit many-to-many relations are represented by an explicit join model in a v8 contract. [Prisma comparison](https://www.prisma.io/docs/orm/coming-from-prisma-orm-7#schema)

This package currently recognizes UUIDs from `field.nativeType[0] === "Uuid"` or documentation, generates `JsonValue` only for the v7 `Json` scalar, derives generated fields from DMMF defaults/`@updatedAt`, and synthesizes implicit-M:N `A`/`B` join schemas. An adapter must make these semantics explicit; feeding contract declarations into the DMMF-specific code is not a safe conversion.

### 3. DateTime changes the emitted runtime contract

In Prisma 8 PostgreSQL, `DateTime` reads/writes as `Temporal.Instant`; users can choose `TimestamptzString` for strings. Generated v7 output in this repository deliberately uses `Schema.DateFromSelf`, so its decoded and encoded values are JavaScript `Date`; the package separately exports `DateFromInput` for consumers that need `Date | string` on an input boundary. Its Kysely utilities also inspect Effect `SchemaAST` directly. A v8 backend cannot reuse the generated mapping without a deliberate Temporal/Date/string policy and boundary checks. [Prisma comparison: DateTime](https://www.prisma.io/docs/orm/coming-from-prisma-orm-7#schema)

### 4. Tooling and package/runtime changes matter only when support is added

A v8 migration is PostgreSQL-only today and is designed to keep v7 and v8 side by side. It requires relocating the v7 CLI/config to `@prisma/prisma7`/`prisma7.config.ts`; ordinary `prisma` becomes v8. Prisma documents a Node 22.18+ prerequisite. This repository is a generator library rather than a Prisma Client application, so it has no routes or migrations to migrate, but its own fixture/integration matrix and documentation would need both protocol paths during an eventual compatibility effort. [Incremental migration guide](https://www.prisma.io/docs/guides/upgrade-prisma-orm/postgresql)

Prisma 8 also replaces `generate`, `migrate dev`, and `migrate deploy` with `contract emit`, `db update` or `migration plan`, and `db migrate`; there is no `migrate reset`. These are not runtime-helper changes, but they prevent a Prisma-8 README example from using this package's current v7 invocation. [Prisma command comparison](https://www.prisma.io/docs/orm/coming-from-prisma-orm-7#commands) · [`migration plan`](https://www.prisma.io/docs/cli/migration-plan)

## Effect 3.21.2 → 3.22.2: material delta only

The package uses public `effect` APIs: `Schema` constructors/combinators, `Schema.Schema.Type`/`Encoded`, schema annotations, and `SchemaAST` constructors/type guards. Repository and generated-code surfaces include `Schema.Struct`, `Enums`, `Literal`, `UUID`, `Int`, `BigIntFromSelf`, `DateFromSelf`, `NullOr`, `Array`, `Record`, `Union`, `propertySignature`, `fromKey`, `brand`, and `Never`.

### Effect 4 is explicitly out of scope for the stable upgrade

Effect 4 (`4.0.0-rc.117`) is still prerelease and outside the package's `^3.19.14` peer range. It is **not** a lockfile-refresh candidate. Its first-party migration map nevertheless shows why it must be a separate, deliberate major migration: this repository directly uses APIs that change there—`UUID`, `BigIntFromSelf`, `DateFromSelf`, variadic `Union`/`Literal`, object-form `Record`, `annotations`, and `fromKey`. Treating an Effect 4 update as part of Prisma work would mix two independent schema-contract rewrites. [Effect v3→v4 Schema migration map](https://github.com/Effect-TS/effect/blob/main/migration/schema.md) · [Effect 4 RC announcement](https://effect.website/blog/releases/effect/40-rc) · [Effect registry](https://registry.npmjs.org/effect)
